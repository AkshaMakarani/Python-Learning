# Customer Support Ticket Classification (NLP)

Automatic routing of customer support tickets into four departments (Billing, Technical Issue, Delivery, and Account Issue) using classical NLP and linear classifiers. Covers the full pipeline: weak label generation, NLTK/spaCy preprocessing, TF-IDF feature engineering, model comparison, and error analysis.

Built on the [Twitter Customer Support dataset](https://www.kaggle.com/datasets/thoughtvector/customer-support-on-twitter), using the first 100,000 rows filtered to 54,948 inbound customer tweets.

## Pipeline

**Ingestion & EDA → weak label generation → NLP preprocessing → TF-IDF → model training → evaluation & error analysis**

The dataset has no category labels, so labels are generated by **keyword-based weak supervision**: each tweet is scored against four keyword sets and assigned the best-matching category. Tweets matching nothing are dropped. This yields 26,049 labelled tickets (25,894 after removing rows that clean to empty), heavily skewed toward Technical Issue (13,632), with Account Issue the smallest class (1,895).

Preprocessing removes mentions, URLs, hashtags, and non-alphabetic characters, then tokenises, drops NLTK stopwords, and lemmatises with WordNet. Vocabulary drops from 34,889 raw tokens to 18,056, and the top tokens shift from stopwords (`i`, `the`, `to`) to domain terms (`service`, `account`, `order`, `app`).

Features are TF-IDF with unigrams and bigrams, `min_df=3`, `max_df=0.9`, `sublinear_tf=True`, and a 15,000 term cap justified by an ablation over five vocabulary sizes. The vectoriser is fitted on the training split only. The test set is transformed, never fitted, to avoid leakage.

## Results

Held-out test set, 5,179 tickets (20%, stratified):

| Model | Accuracy | F1 Macro | F1 Weighted |
|---|---|---|---|
| Multinomial Naive Bayes | 0.803 | 0.696 | 0.787 |
| Logistic Regression | 0.931 | 0.905 | 0.930 |
| **Linear SVM** | **0.937** | **0.916** | **0.936** |

Linear SVM wins, as expected for high-dimensional sparse text. Cross-validation F1 (0.909 ± 0.004) sits within 0.007 of the test score, so there is no sign of overfitting. Per class, Account Issue is the weakest (F1 0.84), being the smallest class and sharing vocabulary with Billing. Misclassification rate is 6.4%.

The `max_features` ablation is flat from 3,000 terms upward (F1 0.905 to 0.910 across all five settings), so vocabulary size is not the binding constraint here.

## The main caveat

**Reported accuracy measures agreement with the keyword rule, not real-world correctness.** A manual spot-check of 10 tweets per category put weak-label accuracy at roughly 80%, so a model scoring 94% against those labels is largely learning to reproduce the keyword heuristic, including its mistakes. True accuracy against human judgement would be meaningfully lower. Treating the 80% figure as a ceiling, the honest read is that the classifier has essentially saturated the labelling function, and further gains require better labels rather than better models.

Two related limits: the 28,899 tweets matching no keyword (over half the corpus) are discarded rather than routed, so the system has no fallback path; and error analysis shows non-English tweets and off-topic complaints being confidently assigned to a category.

```bash
pip install pandas numpy scikit-learn nltk spacy wordcloud matplotlib seaborn
python -m spacy download en_core_web_sm
```

Download `twcs.csv` from Kaggle and update the path in the ingestion cell. NLTK corpora download automatically on first run.

## Possible extensions

Human-annotate a few thousand tickets to get a real evaluation set and measure the weak-label gap directly. Add an "Other" or low-confidence class so unmatched tickets are routed to a human queue. Compare against a transformer baseline (DistilBERT) to see how much the bag-of-words ceiling is costing.
